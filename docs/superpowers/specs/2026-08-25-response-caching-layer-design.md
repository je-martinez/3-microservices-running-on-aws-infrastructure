# Response Caching Layer Design

A shared-Redis, HTTP-layer response cache across all three 3MRAI services (Users/Fastify,
Orders/.NET Minimal APIs, Tracking/FastAPI), reporting hit/miss/bypass via an `X-Cache`
response header (see [http.dev/x-cache](https://http.dev/x-cache)).

## Context

Redis/Valkey already exists in this repo: `infra/modules/redis` provisions an ElastiCache
replication group, locally backed by a Floci `floci-valkey-<id>` container (see
[[floci-elasticache-two-ports-and-provider-panic]] for the local emulation quirk). Today only Users
consumes it, for password-reset codes with a 10-minute TTL. **No new infrastructure module is
needed for this design** — it reuses the existing deployment.

`ioredis` is already a dependency of Users. Orders needs `StackExchange.Redis`; Tracking needs
`redis-py`.

`REDIS_HOST` / `REDIS_PORT` are already generated by `make env-file` but currently only reach
`.env.local.users`. Per [[env-files]], these are AUTO-GENERATED — the generator changes to
also emit them into `.env.local.orders` and `.env.local.tracking`; the files are never
hand-edited.

nginx (`infra/modules/compute/nginx/nginx.conf`) already has `location` blocks for
`/v1/orders`, `/v1/products`, `/v1/cart`, `/v1/trackings`, and the default `/` for Users. No
new route wiring is required for this design — but per [[testing]], the gateway E2E layer
must prove the `X-Cache` response header survives both the API Gateway and nginx, since a
gateway can silently strip an unknown response header and that failure is invisible from the
service port.

## Decisions

### Scope and location

All three services (Users, Orders, Tracking) share the one already-deployed Redis instance.
Not in-memory: a per-replica cache does not propagate invalidation across Fargate tasks. Not
two-level (in-memory + Redis): a single shared layer keeps invalidation correctness simple and
matches the existing Redis footprint.

### Approach — HTTP-layer interceptor per service

An HTTP-layer interceptor per service, not cache-aside written into each handler and not
edge/nginx caching.

- **Rejected: cache-aside in the handler.** Every handler author has to remember to call the
  cache, in the right order, on every route. A new endpoint can silently omit it.
- **Rejected: edge/nginx caching.** Explicit purge from the write path is not workable in
  nginx OSS or in real AWS API Gateway.
- **Chosen: HTTP-layer interceptor.** On a hit the handler never executes at all, and the
  `X-Cache` header is emitted from exactly one place per service, so a newly added endpoint
  cannot silently omit it — the interceptor is opt-in per route (see
  [Three components per service](#three-components-per-service)), but the header contract
  itself is centralized rather than duplicated per handler.

### Header contract

See [[x-cache-response-header]] for the full contract (this spec propagates it there):

- `X-Cache: HIT` plus `X-Cache-TTL: <seconds remaining>`.
- `X-Cache: MISS` — no TTL header.
- `X-Cache: BYPASS` when Redis was unavailable. BYPASS is deliberately distinct from MISS so a
  Redis outage does not read as a poor hit-rate in the metrics; it is excluded from the
  hit-rate denominator.

### Failure mode — fail open

50ms timeout per Redis operation. On timeout/error: fall through to the database, respond
`BYPASS`, log `WARN` with `app_event=cache_unavailable` and a machine-readable `reason`, per
[[logging-context]]. A cache-write failure never affects the response. Governing rule: **the
cache may never break or degrade a read.**

### Invalidation

Explicit, from the write path, **after** the write has persisted — never before. Invalidating
first lets a concurrent read repopulate the stale value between the invalidation and the write
landing.

### Kill switch

`CACHE_ENABLED` per service, sourced from the generated env file (see [[env-files]]). When
`false` the interceptor is skipped entirely and no `X-Cache` header is emitted. Two purposes:
enabling the load-test A/B comparison, and giving an immediate production out if the cache
ever serves incorrect data.

## Three components per service

Same conceptual shape in all three services; idiomatic implementation per stack.

1. **`CacheGateway`** — transport layer: Redis client, JSON serialization, the 50ms timeout,
   key construction, and metric/span/log emission. Surface:
   - `get(key) -> {hit, value, ttlRemaining}`
   - `set(key, value, ttl)`
   - `invalidate(keys...)`
2. **`CachedRead` interceptor** — applied per cacheable route:
   - Users (Fastify): a `preHandler` + `onSend` pair.
   - Orders (.NET Minimal APIs): an `IEndpointFilter` applied as `.WithCache(...)` at route
     mapping.
   - Tracking (FastAPI): a dependency plus response wrapping.

   On hit: return the cached body with `X-Cache: HIT` + `X-Cache-TTL` headers, without
   executing the handler. On miss: let the handler run, store the response only if it
   returned `200`, emit `X-Cache: MISS`. Non-200 responses are never cached.
3. **`CacheInvalidator`** — called explicitly by the write-path command handlers, after the
   write persists.

### Fourth component — the identity-mapping cache (Orders and Tracking only)

Because every response key carries `user_id` (see [Accepted trade-off](#accepted-trade-off--user_id-in-every-key)),
the lazy `cognito_sub -> user_id` resolution from [[current-caller-context]] must run
**before** the response key can even be built. That means it executes on every request,
including cache hits — in Tracking that is a gRPC call to Users sitting on the critical path
of what should be a fast hit, which erodes much of the saving the response cache is meant to
provide. The response-caching layer described above does not, by itself, cache gRPC calls.

**Resolution: cache the identity mapping itself, as a fourth, separate component.**

| Key | TTL | Invalidation |
|---|---|---|
| `identity:sub-to-user:v1:{cognito_sub}` | 1 h | Cognito webhook, and user deletion (soft-delete) |

- Lives in **Tracking and Orders only** — both resolve `user_id` from `cognito_sub`. It does
  **not** live in Users, where `user_id` comes directly from the authenticated query and needs
  no resolution.
- It is consulted **before** the response key is built. A hit here removes the gRPC call (or,
  in Orders, the local DB lookup) from the critical path entirely. On a double hit — identity
  cache and response cache both hit — Tracking touches neither the network nor MySQL.
- Same fail-open contract as the response cache: 50ms timeout, falling back to the normal
  gRPC/DB resolution on failure. A miss or a timeout here never blocks the request; it just
  means the request pays the resolution cost it would have paid anyway.
- The 1h TTL is safe because the mapping is effectively immutable — a `cognito_sub` never maps
  to a different `user_id`. Webhook invalidation covers account deletion, the one case where
  the mapping should stop resolving.
- **Correctness detail:** when invalidating on user deletion, the user's *response*-cache
  entries must be deleted too, or they linger until their own TTL even though the identity
  behind them is gone. The per-user key index already required for
  [invalidating `my-orders` and the tracking list keys](#invalidation-matrix) is exactly what
  makes this possible — the same index drives both cleanups.

## Cache keys and TTLs

Every key carries **both** `cognito_sub` and `user_id`, except the product catalog, which
belongs to no user. A `v1` segment allows mass invalidation by version bump if a DTO shape
changes.

| Endpoint | Service | Key | TTL | Reason |
|---|---|---|---|---|
| `GET /v1/products` | Orders | `orders:products:v1` | 10 min | Shared catalog, near-immutable; highest read/write ratio in the repo and the only entry shared across users |
| `GET /v1/cart` | Orders | `orders:cart:v1:{sub}:{user_id}` | 60 s | Highly volatile; TTL is only the safety net, correctness comes from invalidation on every cart PUT/DELETE and on order creation |
| `GET /v1/orders/my-orders` | Orders | `orders:my-orders:v1:{sub}:{user_id}:t{0\|1}` | 2 min | Changes only when an order is created; `t{0\|1}` is `includeTracking`, which changes the body |
| `GET /v1/orders/{orderId}` | Orders | `orders:order:v1:{sub}:{user_id}:{orderId}:t{0\|1}` | 2 min | An order is immutable except for its associated tracking |
| `GET /v1/trackings/{order_id}` | Tracking | `tracking:order:v1:{sub}:{user_id}:{order_id}` | 60 s | Advances via carrier webhook; short TTL plus invalidation on `PUT /status` |
| `GET /v1/trackings` | Tracking | `tracking:list:v1:{sub}:{user_id}:{hash(order_ids)}` | 60 s | `order_ids` is an arbitrary list; normalize (sort + dedup) then hash to bound key cardinality |
| `GET /v1/users/me` | Users | `users:me:v1:{sub}:{user_id}` | 5 min | Profile, rarely changes; invalidated on `PATCH /me` and the Cognito webhook |
| identity mapping (Orders, Tracking) | Orders, Tracking | `identity:sub-to-user:v1:{cognito_sub}` | 1 h | Effectively immutable mapping; consulted before the response key is built, removing the gRPC/DB resolution from the hit path |

Explicitly excluded from caching: `/v1/health` (must reflect real state), every `e2e-*`
endpoint, and all `POST`/`PUT`/`PATCH`/`DELETE`.

### Accepted trade-off — `user_id` in every key

Including `user_id` in every key (alongside `cognito_sub`) is an accepted requirement, not an
oversight, recorded here as a named risk. In Orders and Tracking this forces the lazy
`user_id` resolution described in [[current-caller-context]] — a local DB query in Orders, a
gRPC call to Users in Tracking — on read paths that today never trigger it, since laziness is
the point of that pattern. This adds real cost to the read path, including on a cache **hit**.

The dedicated load-test scenario (see [Observability](#observability)) measures p95 with and
without the cache precisely so this cost is visible. If the Tracking gRPC call turns out to
consume the caching savings, that evidence comes from the load test and the decision can be
revisited with data — it is not revisited here.

**This residual cost is now bounded, not eliminated.** The identity-mapping cache described in
[Fourth component](#fourth-component--the-identity-mapping-cache-orders-and-tracking-only)
means the gRPC/DB resolution is paid only on an identity-cache miss, not on every request —
the cost is bounded by the identity cache's own miss rate rather than paid unconditionally.
The load-test A/B reports the identity-cache hit-rate alongside the response-cache hit-rates
per endpoint, so the two effects are visible separately.

## Invalidation matrix

| Write | Keys removed |
|---|---|
| `PUT /v1/cart`, `DELETE /v1/cart` | `orders:cart:v1:{sub}:{user_id}` |
| `POST /v1/orders` | the user's cart key + `orders:my-orders:v1:{sub}:{user_id}:*` + `orders:products:v1` (stock changed) |
| `PUT /v1/trackings/{id}/status` (carrier webhook) | `tracking:order:*:{order_id}` and the owner's list keys |
| `PATCH /v1/users/me`, Cognito webhook | `users:me:v1:{sub}:{user_id}` |
| Cognito webhook (identity change), user deletion (soft-delete) | `identity:sub-to-user:v1:{cognito_sub}` **and** all of that user's response-cache entries (via the per-user key index) |

Three correctness details:

- **The carrier webhook does not know the owner.** It arrives with `order_id` and
  `x-api-key`, no `x-user-id`. To invalidate a key carrying `{sub}:{user_id}` it must first
  resolve the owner by reading `cognito_sub` from the tracking row itself, before deleting.
- **Invalidating `my-orders` and the tracking list keys requires deleting several keys with a
  variable suffix** (`t0`/`t1`, the `order_ids` hash). This is solved with a per-user key
  index — a Redis SET holding that user's live keys — **not** `KEYS`/`SCAN`, which is O(N)
  over the whole keyspace and is discouraged in production.
- **Deleting the identity mapping on user deletion is not enough on its own.** The user's
  response-cache entries must be deleted in the same operation, or they linger, keyed by a
  `user_id` whose owning identity mapping no longer exists, until their own (short) TTL
  expires. The same per-user key index used for `my-orders`/list-key cleanup drives this
  cleanup too — one index, two invalidation paths.

## Observability

1. **Metrics.** Counter `cache_requests_total{service, key_prefix, result=hit|miss|bypass}`
   plus histogram `cache_operation_duration_ms{operation=get|set}`. Hit-rate is computed in
   OpenObserve as `hit / (hit + miss)`; `bypass` is excluded from the denominator. The
   identity-mapping cache uses its own `key_prefix` (`identity:sub-to-user:v1`) on the same
   counter — its hit-rate will sit near 100% given the 1h TTL on an effectively immutable
   mapping, and it **must never be averaged together** with the response-cache hit-rates or
   both numbers become meaningless.
2. **Tracing.** A child span per operation (`cache.get`, `cache.set`) with attributes
   `cache.result`, `cache.key_prefix`, `cache.ttl_remaining`. **The full key must never go
   into a span** — it carries `cognito_sub` and `user_id`, and a span is an export destination
   like any other; only the prefix is attached. Per [[ADR-0019-distributed-tracing-opentelemetry]],
   traces go to OpenObserve alongside logs.
3. **Logging.** `cache_result` is added to the shared logging context in all three services,
   alongside `trace_id`/`cognito_sub`/`user_id` (see [[logging-context]]). Omitted — never
   null — on non-cacheable routes.
4. **Load test.** A dedicated Gatling scenario runs the same traffic profile twice, cache
   enabled and disabled via `CACHE_ENABLED`, reporting p50/p95/p99 and hit-rate per endpoint,
   **plus the identity-cache hit-rate reported alongside the response hit-rates** so the two
   effects on Tracking's/Orders' critical path are visible separately. Lives beside E2E in
   `e2e/load-tests/`, per the repo's load-testing conventions.

Per [[ADR-0019-distributed-tracing-opentelemetry]] and [[ADR-0018-observability-openobserve]],
endpoint/protocol/exporter configuration goes in environment variables, never in SDK code —
this design introduces no exception.

## Testing

All three layers per [[testing]], for every cached endpoint:

- **Unit/integration.** Hit, miss, TTL expiry, invalidation after a write, fail-open with
  Redis down, and cross-user isolation (user B never sees user A's cached entry) as an
  **explicit** test, not an implicit one.
- **Internal E2E** (direct service URL). Two consecutive GETs -> `MISS` then `HIT`; an
  intervening write -> back to `MISS`.
- **Gateway E2E with a real Cognito JWT.** Confirms `X-Cache` survives the API Gateway and
  nginx. Not redundant with the internal layer — a gateway can strip unknown response headers,
  and that failure is invisible from the service port.
