# Web App Phase 2 — Real Gateway Calls

## Context

The web app (`apps/web`, Angular 21 + NgRx signals + Tailwind 4) shipped phase 1 as a fully
designed, fully static front end. 15 files import from `src/app/fixtures/`. There is no HTTP
client, no `provideHttpClient`, no auth session, and no `NG_APP_API_GATEWAY_URL` — the app
currently has no way to reach the gateway at all. Phase 2 replaces the data source without
redesigning the screens.

## The blocker found during design: no CORS anywhere

Neither `infra/modules/api-gateway/main.tf` nor `infra/modules/compute/nginx/nginx.conf`
configures CORS. A browser calling the gateway from a different origin would be blocked at the
preflight on every request. The E2E suite never caught this because Playwright issues
server-to-server requests, which have no origin policy.

Resolution: **same-origin proxying, not CORS**. The nginx that already serves the built app
(`apps/web/nginx.conf`, published on host port 3004) gains a `location /v1/` block proxying to
the gateway, and `ng serve` gets an equivalent `proxy.conf.json` for development. The browser
then only ever talks to its own origin and no preflight occurs. This also mirrors production
(CloudFront in front of both app and API) better than opening CORS would.

Consequence: `NG_APP_API_GATEWAY_URL` carries the RELATIVE path `/v1`, not Floci's URL. Floci's
ugly and non-deterministic gateway URL (`/restapis/<api-id>/$default/_user_request_`, re-minted
on every apply) lives in the nginx config, generated by `make env-file` — never compiled into
the bundle. See [[env-files]] for the generated-vs-hand-edited env file split this depends on.

## Proxy implementation traps (found at design time)

These were verified by reading `infra/modules/compute/nginx/nginx.conf` and
`.env.local.infra` during design. They must not be rediscovered during implementation.

- **`$default` is a literal in the gateway URL, and nginx has no escape for it.**
  **CORRECTED 2026-09-04 (JE-237) — the original fix documented here did not work and was
  disproven during implementation.** The generated `API_GATEWAY_URL` is
  `http://localhost:4566/restapis/<api-id>/$default/_user_request_`. In an nginx `proxy_pass`,
  `$default` parses as a VARIABLE and expands to the empty string, silently turning the path
  into `/restapis/<id>//_user_request_`. nginx has **no escape for a literal `$` anywhere in
  its configuration** — all of the following were tested against a real nginx and all fail:
  single quotes (`set $stage '$default'` still interpolates; nginx refuses to start with
  `unknown "default" variable`), a backslash (`"\$default"`), a `map` with a `$` default
  value, and `rewrite` (double-encodes to `%2524`). The only working route is to
  **percent-encode it as `%24` directly in the `proxy_pass` path.** Verified against a live
  Floci: `%24default` and `$default` both return 200 with an identical path reaching the
  backend.
- **A `proxy_pass` containing a variable does NOT append the unmatched request URI.** nginx
  appends the remaining URI only when `proxy_pass` is a static string; the moment it contains
  a variable (as it must here, to force per-request DNS resolution — see the resolver trap
  below), `/v1/users/health` reaches the gateway as a bare `/v1`. This is the worst failure
  mode of the set because it returns **200 from the wrong route** rather than an error. The
  fix is to append `$request_uri` explicitly.
- **The container and the host reach Floci by different names.** `localhost:4566` is a HOST port
  mapping. From inside the compose network the web container must address Floci by its container
  name instead, so the value nginx needs is NOT the same string the E2E suite reads from
  `.env.local.infra`. Two consumers, two values, one contract.
- **Copy the resolver pattern from the gateway's nginx.** `infra/modules/compute/nginx/nginx.conf`
  uses `resolver 127.0.0.11 valid=5s;` together with `set $backend <name>;` so Docker DNS is
  resolved per request. Without it nginx pins the resolved IP at startup, and a restarted Floci
  becomes permanently unreachable until nginx itself restarts.
- **`ng serve` needs its own proxy target.** `proxy.conf.json` points at `localhost:4566` from the
  developer's host, which is a different target than the container path in the trap above. Both
  configs implement the same contract and must be changed together.

### Implementation shape

`apps/web/nginx.conf` is an **envsubst template** mounted at
`/etc/nginx/templates/default.conf.template`, rendered at container start so the per-apply
gateway id reaches nginx. `NGINX_ENVSUBST_FILTER=^API_GATEWAY_` restricts substitution to
those variables — without the filter, envsubst also expands nginx's own `$uri`/`$host`/
`$request_uri` to empty and the SPA fallback silently serves nothing. The `ng serve` half is
`apps/web/proxy.conf.json`, generated by `make env-file` and gitignored, with
`apps/web/proxy.conf.example.json` as the committed contract. Note that the `ng serve` proxy
writes `$default` PLAINLY — http-proxy-middleware performs no expansion, so only the nginx
side needs `%24`.

## Architecture — seven pieces under `core/`

- `core/http/api-client.ts` — `provideHttpClient(withInterceptors(...))` plus a typed
  `ApiError`. Base URL read from `APP_CONFIG`.
- `core/auth/token-store.ts` — AES-GCM encryption with a `CryptoKey` generated
  `extractable: false`, the key object itself stored in IndexedDB. The key bytes are never
  readable from JS, which blocks storage scraping, devtools dumps and backups. It does NOT
  stop an active XSS that calls `decrypt()` in the page — no SPA can. Surface: `read()`,
  `write(tokens)`, `clear()`.
- `core/auth/session-store.ts` — an NgRx `signalStore`, same pattern as the existing
  `OverlayStore`. Holds the current user and `isAuthenticated`. Single source of truth for
  session state.
- `core/auth/auth-interceptor.ts` — attaches `Authorization: Bearer <accessToken>`. Skips
  public routes: `login`, `register`, `refresh`, `otp/*`, `password/forgot`,
  `password/confirm`.
- `core/auth/refresh-interceptor.ts` — on a 401, calls `POST /v1/users/refresh` once and
  retries. CRITICAL: the in-flight refresh MUST be shared across concurrent requests
  (`shareReplay`), or five parallel calls fire five refreshes and four fail. On refresh
  failure, clear the session and redirect to `/login`. Contract note: `/v1/users/refresh`
  returns ONLY `idToken` + `accessToken` — it does NOT rotate the refresh token, so the
  original refresh token is retained.
- `core/auth/guards.ts` — `authGuard` protecting `/`, `/orders`, `/checkout`, `/profile`;
  `guestGuard` bouncing authenticated users away from `/login`. The `authGuard` MUST await
  rehydration of the token from IndexedDB, which is asynchronous — otherwise a reload on
  `/orders` evicts the user before their session is read.
- `core/api/*.ts` — one service per domain: `users-api`, `catalogue-api`, `orders-api`,
  `cart-api`.

## Types

`fixtures/api-types.ts` moves to `core/api/types.ts` (these are contract types, not fixture
types) and is EXTENDED with what it does not currently model: `CartDto`, `CartLineDto`, and
`Money` (`{cents, amount, formatted, currency}`).

Money trap, per [[money-representation]]: the cart returns a server-computed `formatted`
string. Render THAT — do not re-round in the client, or the preview diverges from what is
actually charged.

`catalogue.fixture.ts`, `orders.fixture.ts` and `user.fixture.ts` are deleted.
`notifications.fixture.ts` STAYS, marked with a `CONTRACT:` comment stating that no service
exposes notifications yet.

## The cart stops being fake

The largest piece. `cart-drawer.ts` currently fakes contents with `PRODUCTS.slice(0, 3)`. It
becomes server-backed: `GET /v1/cart` on sign-in, `PUT /v1/cart` on mutation, and the UI begins
rendering the real `available`, `unavailableReason` and `canCheckout` fields — states the
design already accounts for but which are unreachable today. Because `PUT` replaces the whole
cart, mutations MUST be serialized in the store; two in-flight PUTs clobber each other.

## Decisions taken

- Token storage: encrypted IndexedDB with a non-extractable `CryptoKey` (chosen over
  localStorage; the limits are stated honestly above).
- Cart: full server-backed cart in this branch.
- Notifications and `Address`: stay as marked fixtures — no service exposes them, and
  inventing a contract would fail at runtime.
- `GET /v1/products` requires auth (`auth = true` at the gateway), so the app is login-first:
  unauthenticated visitors land on `/login`. The alternative (making products public) was
  considered and rejected as a backend product decision outside this branch's scope.

## Testing

Per [[testing]], adapted for a client app rather than a new endpoint:
- Vitest: the refresh interceptor including the CONCURRENT case, the encrypted token store,
  the guards.
- Playwright in `e2e/tests/web/`: real login through the gateway, session surviving a reload,
  eviction on expiry. These specs open a browser window — they must honor the existing
  `web-browser.ts` rule and ASK before launching.

## Work plan — 9 issues, one commit each

Branch `feature/web-gateway-integration`, cut from `feature/web-app-foundation` (this
continues that phase, not `main`). See [[git-workflow]] for the branch-flow convention this
follows.

1. nginx + `ng serve` proxy, `NG_APP_API_GATEWAY_URL`, `make env-file` wiring — no deps
2. `core/api/types.ts` (move + `CartDto`/`Money`) — no deps
3. Encrypted token store (IndexedDB + non-extractable `CryptoKey`) — no deps
4. HTTP client + auth interceptor — needs 1, 2
5. Session store + refresh interceptor — needs 3, 4
6. Route guards + boot rehydration — needs 5
7. Auth screens against Users (password, OTP, reset) — needs 5
8. Catalogue, orders and profile wired; fixtures deleted — needs 4, 6
9. Real cart and checkout (`GET`/`PUT`/`DELETE /v1/cart`) — needs 8

Issues 1–3 are independent and parallelizable; from 4 onward the chain is sequential.
