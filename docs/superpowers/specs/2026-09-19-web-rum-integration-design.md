# Web RUM — Browser Telemetry Integration Design

## Context

The web app (`apps/web`, Angular 22, zoneless, NgRx signals) has zero browser telemetry.
Verified: no `@opentelemetry/*` package in `apps/web/package.json`, no `traceparent` anywhere
in `apps/web/src`. Every trace in the system is born at the API gateway, so everything the
user actually experiences — document load, route navigation, perceived performance, JS
errors — is a blind spot. [[ADR-0019-distributed-tracing-opentelemetry]] instrumented the
services; this extends the same OTel story to the browser, with logs and traces both landing
in OpenObserve.

Scope is local only (Floci + docker compose). The AWS/Terraform path — a deployed collector,
an `/otlp` location in the ECS nginx task — is explicitly out of scope for this spec; the user
confirmed this during brainstorming.

## Decision 1 — the SDK boots before `bootstrapApplication`, behind an off-by-default flag

New directory `apps/web/src/app/core/observability/` with `rum.ts` (SDK init),
`rum-propagation-interceptor.ts`, `rum-error-handler.ts`. `main.ts` calls `initRum()` before
`bootstrapApplication`. Stated concretely: `document-load` reads the Navigation Timing API; if
the SDK starts inside an Angular provider that span has nothing left to record, or arrives
with incomplete timings.

Flag `NG_APP_RUM_ENABLED`, parsed in `src/app/core/config/app-config.ts` exactly like the
existing four (`=== 'true'`), added to the `APP_CONFIG` literal by spelling out the full
`import.meta.env.NG_APP_RUM_ENABLED` access — per `apps/web/CLAUDE.md` §2c, destructuring
there ships a bundle reading `undefined` silently. Off by default.

When off, `initRum()` returns immediately: no providers, no exporters, no listeners. This
matters because the collector sits behind compose's `observability` profile — a plain `make
up` leaves it down, and a default-on RUM would spam failed exports against a host that does
not resolve, the same failure `docker-compose.yml` already documents for the services ("8 in 2
min on an idle stack").

Deliberate asymmetry with `NG_APP_WS_URL`: that one warns when unset because a user-facing
feature silently disappears. RUM off costs the user nothing, so it stays silent — a
`console.warn` on every dev boot would be pure noise.

`apps/web/.env.example` documents the var at the same level of detail as its neighbours:
build-time (restart `pnpm dev`), and requires `make observability-up`.

## Decision 2 — telemetry leaves same-origin through `/otlp`, and the proxy has two halves

The browser exports to `/otlp`, same-origin, exactly as `/v1` and `/geocode/` already do
(see [[2026-09-04-web-gateway-integration-design]] and
[[2026-09-06-address-geocoding-proxy-design]]). Three sub-paths, one per signal, because
OTLP/HTTP uses a distinct path per signal: `/otlp/v1/traces`, `/otlp/v1/metrics`,
`/otlp/v1/logs`. One `location` covers all three by preserving the path under the prefix.

The critical part, easy to miss: the proxy has two halves that must move together.

1. `apps/web/nginx.conf` — the container half. A `location /otlp/` proxying to the collector,
   with `resolver 127.0.0.11` like the rest (the collector may be down when nginx starts;
   without a dynamic resolver nginx fails to *start* rather than failing the request). This
   location must **not** be access-logged: telemetry logging its own delivery lands in the
   `nginx` stream and generates more telemetry.
2. `infra/environments/local/scripts/generate_env_files.py` — the `ng serve` half. Verified:
   `proxy.conf.mjs` is gitignored and generated by this script; only `proxy.conf.example.mjs`
   is committed and nothing reads it. Adding the location to nginx alone leaves RUM working in
   the container and broken under `pnpm dev` — silently, because a failed export does not
   break the app. The script emits the `/otlp` entry targeting `http://localhost:4319` (the
   published port, mirroring how `/v1` targets `localhost:4566` and not `floci:4566`), and
   `proxy.conf.example.mjs` is updated to document the shape.

`make env-file` must be re-run to materialise the new `proxy.conf.mjs` — a plan step, not an
assumption.

Rejected: an absolute endpoint with CORS on the collector. It would break the same-origin
contract `app-config.ts` documents ("nothing in this repo sends CORS headers") and bake an
origin into the bundle that differs between local and prod.

## Decision 3 — three RUM streams, isolated by a second OTLP receiver rather than by filters

Three own streams in OpenObserve: `rum_traces`, `rum_metrics`, `rum_logs`, each with its own
`otlp_http/openobserve_rum_*` exporter carrying its stream-name header — the pattern the
config already repeats nine times.

Departure from house style, stated rather than left implicit: the existing config's rule is
that pipelines sharing a receiver use exact-complement filters so every record lands in
exactly one stream. The RUM pipelines need none of that because they separate by receiver,
not by filter. A second OTLP receiver `otlp/rum` listens on port 4319; the proxy points there.
The existing `otlp` receiver keeps serving the services on 4318, and the existing `traces`
pipeline is not touched.

Why this over one receiver filtered by `service.name`: the isolation becomes structural
instead of depending on an attribute being set correctly — a browser cannot leak into the
backend traces stream even if someone misnames the resource. Honest cost: one more published
port and one more receiver in the config.

All three pipelines put `memory_limiter` before `batch`, following the comment already on the
traces pipeline (limiting after the batcher has buffered limits nothing). No
`transform/parse_body`: OTLP arrives structured, there is no JSON-in-a-string body.

A RUM dashboard under `observability/dashboards/*.dashboard.json` (imported by `make
observability-dashboards`) is in scope, since that is where vitals are actually read. Note it
as the first candidate to split into its own issue if the delivery proves too large.

## Decision 4 — `traceparent` is injected by an Angular interceptor, which starts its own span

`rumPropagationInterceptor` is registered last in the chain: `[refreshInterceptor,
authInterceptor, rumPropagationInterceptor]`. This is what joins the browser trace to the
gateway and service traces under one `trace_id` — the actual point of the exercise.

Why an interceptor and not the SDK's XHR instrumentation: `ApiClient` already declares as a
contract that every gateway call goes through it, so an interceptor inherits that guarantee;
XHR instrumentation instead propagates per `propagateTraceHeaderCorsUrls`, a pattern list that
would hand-duplicate what `APP_CONFIG.apiGatewayUrl` already knows. Ordering matters too — the
interceptor sees the request with its `Authorization` already attached, at the same point the
repo puts the rest of its cross-cutting HTTP logic.

The interceptor starts its own short-lived CLIENT span around each gateway call and injects
`traceparent` from that span's context — it does not rely on an ambient active span. The span
carries `http.request.method` and `http.route`, the gateway-relative route from `gatewayPath()`,
never `req.url` — a full URL can carry a query string. It is ended exactly once, on success,
error and unsubscribe alike, via `finalize()`, with its status set to ERROR on the error path
and OK otherwise.

The boundary between the interceptor and auto-instrumentation must be written down as a
`CONTRACT:` comment in the interceptor file, phrased as a present-tense prohibition per the
repo's code-comment convention: `document-load` and route navigation go through
auto-instrumentation; HTTP goes through the interceptor. Without it someone re-enables XHR
instrumentation "for completeness" and gets duplicate spans per request.

Note the `refreshInterceptor` interaction so it is not misread as a bug during verification:
when a 401 triggers a refresh and the cloned original is retried, that retry passes through
the chain again and gets its own `traceparent`. Correct — they are two real HTTP requests —
and desirable in the waterfall.

The interceptor's CLIENT span is parented, not root: a page-scoped root span, owned by the
lazily-loaded SDK module and rotated by a root-provided `RumNavigation` service on Angular
Router `NavigationEnd`, with `visibilitychange`/`pagehide` as backstops so it is bounded and
never left open for the tab's lifetime. The interceptor parents its span off that page span via
an explicit parent context, producing one waterfall per page: page span → browser CLIENT spans
→ gateway/service spans, all under one `trace_id`. When no page span exists — the flag is off,
the lazily-loaded SDK has not landed yet, or between navigations — the interceptor still starts
a root CLIENT span and still injects `traceparent`, so a missing page span degrades the
waterfall but never the cross-service join.

Rejected: injecting `traceparent` from the ambient OTel context (`context.active()`) rather
than a span the interceptor owns. `W3CTraceContextPropagator.inject()` writes nothing unless a
span is active in the context it is given. `DocumentLoadInstrumentation`'s root span is active
only inside its own synchronous `context.with(...)` during page load, and the instrumentation
does not expose that span; by the time any HTTP call happens, `context.active()` carries no
span, so the propagator has nothing to inject and every request goes out headerless.

## Decision 5 — vitals become OTLP metrics, JS errors become OTLP logs

Vitals via `web-vitals` 6.2.2: LCP, CLS, INP, plus TTFB and FCP (same API, no extra cost) →
OTLP metrics → `rum_metrics`.

The timing detail correctness depends on: these are not reported at page load. LCP finalises
at first interaction, CLS accumulates over the tab's lifetime, INP only exists after
interaction. The library hands each value to a callback when it is final; sending happens
there, plus a flush on `visibilitychange → hidden`, which is the only reliable moment on
mobile where `unload` does not fire. Flushing on an arbitrary timer publishes provisional
values that look like good data — the same shape as the repo's own `verify-across-full-cycle`
lesson (measuring inside the cycle window yields a false pass).

Errors → OTLP logs → `rum_logs`, from a single source: Angular's custom `ErrorHandler`.
`app.config.ts` already calls `provideBrowserGlobalErrorListeners()`, and Angular's own
implementation of that provider attaches `window.onerror` and `unhandledrejection` and routes
both into the injected `ErrorHandler` — a second, separate pair of listeners would report every
global error twice. The custom `ErrorHandler` delegates to the original after reporting, so the
console still shows the error in dev; a handler that swallows it is worse than none.

Redaction, with teeth: [[logging-context]] forbids logging full bodies, tokens and plaintext
emails. A browser error carries a stack, and a stack can drag values along. What is sent is
bounded to an explicit allow-list: `message`, `stack`, `type`, `route`, `trace_id`, `user_id`,
and for an `ApiError` `status`/`detail` — never the whole serialised error object and never the
failed request's body or query string. `route` is `location.pathname`, never the full URL. An
`ApiError`'s message has its embedded URL's query string stripped before emission. Unknown
fields are omitted, never null.

`cognito_sub` is never emitted, and cannot be: there is no synchronous source for it anywhere
in this app. The JWT is never decoded client-side, and an `ErrorHandler` runs on the error path
— possibly during teardown — so it must not await a token read. `user_id`, the internal
`usr_…` identifier held synchronously by `SessionStore`, is what identifies a session instead.

`trace_id` reaches `rum_logs` only for errors originating from a gateway call: the interceptor
stamps its span's trace id onto the failing response before the context unwinds. A template
error or a null dereference has no active span by the time `ErrorHandler` runs, so the field is
absent there — absent, never null.

## Decision 6 — no service code changes; infra changes are local only

Zero changes to Users, Orders, Tracking, the events-pipeline, or the API gateway routing. The
services run `@opentelemetry/sdk-node` with `auto-instrumentations-node`, whose default
propagator is W3C Trace Context: they already read an incoming `traceparent` and continue that
trace. Today none arrives, so every trace starts at the gateway; RUM simply starts sending
one. The server side does not change — it stops being the trace origin and becomes a link.

Epistemic status, stated honestly: this is the well-founded expectation from the SDK's default
behaviour, not something verified by running it. The end-to-end check in
[Verification](#verification) is exactly what confirms it. If a hop turned out to drop the
header, the fix would be propagator configuration, not business logic.

Infra changes, all local: `observability/otel-collector-config.yaml`, `docker-compose.yml`
(publish 4319), `infra/environments/local/scripts/generate_env_files.py`, and
`apps/web/nginx.conf`.

## Non-goals

- **AbortController / systematic request cancellation.** Deliberately deferred by the user to
  a separate delivery. Recorded so it is not re-derived: today only
  `apps/web/src/app/shared/ui/street-autocomplete.ts` cancels anything (`switchMap` +
  `takeUntilDestroyed`); `AbortController` appears nowhere in `apps/web/src`; and because
  `ApiClient` sits on Angular's `HttpClient`, the natural mechanism is
  `unsubscribe`/`takeUntilDestroyed`, not a literal `AbortSignal`.
- The AWS/Terraform ingest path (deployed collector, ECS nginx `/otlp`).
- Session replay, user-interaction auto-instrumentation (too noisy), and any third-party RUM
  SaaS.

## Packages

Verified live against the registry on 2026-09-19: `@opentelemetry/sdk-trace-web` 2.11.0,
`@opentelemetry/instrumentation-document-load` 0.67.0,
`@opentelemetry/exporter-trace-otlp-http` / `exporter-metrics-otlp-http` /
`exporter-logs-otlp-http` 0.222.0, `@opentelemetry/sdk-metrics` 2.11.0,
`@opentelemetry/sdk-logs` 0.222.0, `@opentelemetry/api-logs` (the error handler needs
`SeverityNumber`), `web-vitals` 6.2.2. Installed with pnpm (never npm) — see
[[package-manager]] if it needs restating, per repo convention.

`@opentelemetry/auto-instrumentations-web` 0.67.0 exists but is **not** adopted wholesale —
only the document-load instrumentation is wanted; pulling the bundle brings user-interaction
noise.

Several of the installed OTel packages are CommonJS and produce build warnings that block
tree-shaking — the reason the SDK is lazy-loaded behind a dynamic import rather than merely
flag-gated at module scope.

## Verification

Per [[2026-08-21-verify-in-the-viewer-not-the-api]], done means seen in the viewer, not an
exporter that returns OK.

- **End-to-end trace**: a real browser flow (login → catalogue → add to cart) produces one
  trace in the OpenObserve waterfall showing the full hierarchy — the page-scoped root span as
  parent of the browser CLIENT spans, which in turn parent the gateway span and the service
  spans — all under the same `trace_id`. Two disconnected traces, or CLIENT spans with no
  parent, is the classic failure and is exactly what this rules out. Verified live: 7 of 7
  CLIENT spans parented; one `trace_id` holding the `/login` page span, its two browser CLIENT
  children, and the Users service's spans in `app_traces`.
- **Vitals**: LCP, CLS and INP carry real values in `rum_metrics` after interacting — not
  merely a created, empty stream.
- **Errors**: a deliberately triggered error appears in `rum_logs` with its stack and
  `trace_id`, and with no forbidden field.
- **Flag off**: with `NG_APP_RUM_ENABLED=false`, zero requests to `/otlp` in the network tab.
  This is the forgotten one, and it is what protects a plain `make up`.
- **Both proxy halves**: verified under `pnpm dev` and in the container. One of the two is not
  "verified".
- **Existing suite green**: `pnpm test`, `pnpm lint`, `pnpm typecheck`, `make lint-comments`.
- **`pnpm build`**: the initial-bundle budget (600 kB, `apps/web/angular.json`) is a real gate
  that `test`/`lint`/`typecheck` do not check — its absence let a 173 kB breach reach the final
  review. The SDK is lazily imported behind the flag specifically to stay under it; the shipped
  initial bundle is 565.97 kB.
- **Known trap, not a RUM bug**: if the trace waterfall returns HTTP 400 (`code 20004`,
  `gen_ai_operation_name`), run `make observability-traces-schema`.

## Implementation split

Two hands, because this is not a `web-impl`-only delivery:

- **`web-impl`** — everything under `apps/web/src` (SDK init, interceptor, error handler,
  vitals, `app-config.ts`, `.env.example`).
- **`infra-impl`** — `observability/otel-collector-config.yaml`, `docker-compose.yml`,
  `infra/environments/local/scripts/generate_env_files.py`, the RUM dashboard JSON, and
  `apps/web/nginx.conf` (it lives under `apps/web/` but is serving infrastructure — assigned
  explicitly rather than left ambiguous).

Real ordering dependency: the ingest path must exist before end-to-end verification can pass.
The SDK can be written in parallel but cannot be called done until the collector receives.
