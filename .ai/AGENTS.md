# 3MRAI — agent instructions

Project instructions for the **3 Microservices Running on AWS Infrastructure
(3MRAI)** repo. These rules take precedence over your default behavior.

> **This file is generated.** It is distilled from `CLAUDE.md` and
> `.claude/agents/` — the source of truth — and regenerated by the repo's config

## Working rules

### Git — confirm every write

**Never commit, push, merge, or open a pull request without explicit user
confirmation.** Leave finished work in the working tree until the user chooses.
Choosing an action authorizes **only** that action — never a merge, never
standing approval. **Never auto-merge.**

This overrides any tool or workflow that commits automatically.

Full rule, including the five options and the branch flow:
`.ai/rules/git-and-commits.md`.

### Commit messages

All commits and PR titles follow **Conventional Commits v1.0.0**:
`<type>(<scope>): <description>`, types
`feat|fix|build|chore|ci|docs|style|refactor|perf|test`, scope = the repo area
(`users`, `orders`, `tracking`, `events-pipeline`, `infra`, `vault`, `agents`).
Attach context references as footers (`Refs:`, `Plan:`, `Spec:`) on a best-effort
basis — enrichment, never a blocker.

### Scripting language — Python first

New scripts are **Python** by default. **JavaScript** only where the task already
lives in the Node ecosystem present here. **Bash** only with a limitation
documented in a comment inside the script — the repo has **zero `.sh` files**.

Infra Python runs from the repo venv by **absolute path** (`.venv/bin/python`),
never plain `python3` off `PATH`. Node is pinned by `.nvmrc` (**24.18.0**);
activate it before any `node`/`npm`/`npx` command.

Full rule: `.ai/rules/scripting-language.md`.

### Env files — generated, never hand-edited

`make env-file` generates **every** env file from Terraform outputs. Each has an
**AUTO-GENERATED** box (rewritten every run) and a **CUSTOM** box (preserved).
Put overrides in CUSTOM; never edit the AUTO box. Services read their file via
compose `env_file:` and declare **nothing** inline — an inline `environment:`
silently beats `env_file:`.

Full rule: `.ai/rules/env-files.md`.

### Logging, tracing, and PII

Every log line carries the shared cross-service context (`trace_id`,
`cognito_sub`, `user_id`, `email_hash`, `order_id`, `duration_ms`). Unknown
fields are **omitted, never null**.

**Never log** passwords, tokens, full request bodies, or a **plaintext email** —
auth flows log a masked form (`jo*****e@gmail.com`), everything else uses
`email_hash`.

There is **no SUCCESS severity**: success is `INFO` + `app_event=*_succeeded`.
**OpenTelemetry config goes in environment variables, not code.**

Full rule: `.ai/rules/logging-and-pii.md`.

### Testing — three layers per endpoint

Every new or changed HTTP endpoint requires **all three**: (1) unit/integration,
(2) internal E2E against the service URL, and (3) **gateway E2E with a real
Cognito JWT**. Internal tests fake the authorizer and never touch the gateway, so
they miss gateway-only bugs. An endpoint without gateway E2E is an **incomplete
change**.

Full rule: `.ai/rules/testing.md`.

### Language

**Converse with the user in Spanish.** **Write documentation content in English**
(note bodies, technical terms, filenames, frontmatter).

### Scope

Stay within what was asked. **No unrequested features, files, or refactors**
(YAGNI).

Full rule for both: `.ai/rules/language-and-scope.md`.

### Documentation vault

The Obsidian vault under `docs/` is the source of truth for technical content:
hybrid domain + type structure, required frontmatter, folder-style tags, a
`## Related` section on every note, and a propagation gate that a spec must pass
before the PR closing its issue. See the prohibition on writing to `docs/` below.

Full rule: `.ai/rules/documentation-vault.md`.

## Prohibitions

Three resources in this repo have a **single designated writer**. In Claude Code
each is a subagent that owns the resource; here there is no such agent and no
tool boundary enforcing it. The prohibition still holds — **propose the change
and wait for explicit confirmation, never write directly.**

These are deliberately **not** listed as roles below. Presenting them as
available roles would invite you to conclude you may perform the write yourself.

- **Writes to `docs/` (the Obsidian vault)** go through the `obsidian-vault`
  agent, the sole writer of the vault, so structure, frontmatter, tags, and
  wikilinks stay consistent. If that agent does not exist in this environment,
  propose the change and wait for explicit confirmation — never write to `docs/`
  directly.
- **Writes to Linear** (milestones, issues, projects, labels, comments, status
  updates) go through the `linear-pm` agent. Reading Linear is free; **every
  write is proposed and waits for explicit user confirmation.** Never create or
  update a Linear object on your own initiative.
- **Git and GitHub writes** (commits, branches, pushes, PRs, merges) may be
  performed directly, but **only after the explicit confirmation** described in
  `.ai/rules/git-and-commits.md`. The `github-ops` agent is an optional helper
  for complex batches, not a required gateway — what is required is the
  confirmation, and it applies equally to you.

## Roles

The repo defines specialized agents. In Claude Code each is a **subagent** with
its own isolated context and a `tools:` allowlist the runtime enforces.

**In this environment the isolation is absent and the tool restriction is
not tool-enforceable.** Nothing stops you from running git while acting as an
implementer. Treat each role's restrictions as a **repo norm you are expected to
respect**, not as a boundary that will stop you.

Roles are **passive context**, not behavior to adopt on your own. Act as one only
when the user asks for that work — do not "become" a role because a description
matches.

### users-impl

Code implementer for the 3MRAI **Users** service (Fastify, Aurora Postgres). Use
to implement a single Users-service task from the plan. Writes **source code
only** — never touches git, never touches Linear. Reads
`services/users/CLAUDE.md` for its stack and conventions and the vault spec note
for the design, implements the task, and leaves the work in the working tree for
the main session to commit.

*In Claude Code this is a subagent whose tools are restricted to
Read/Write/Edit/Bash/Glob/Grep. In this environment that restriction is
not tool-enforceable — treat it as a norm.*

## Not portable

Parts of the source configuration have **no equivalent here** and did not travel.
Do not assume parity with Claude Code:

- **`tools:` allowlists on 9 subagents** — an enforced restriction in Claude
  Code; here only the prose norm stated in each role above.
- **Per-subagent context isolation** — no equivalent in any target provider. A
  section in this file is not an isolated context window.
- **The A/B/C/D/E confirmation menu rendered via `AskUserQuestion`** — the
  *policy* (never write to git without confirmation) travels and is binding; only
  the interactive menu mechanism is Claude-specific.
- **Claude Code plugins and their MCP servers** (superpowers, Linear,
  aws-dev-toolkit, context7, Obsidian) — proprietary; not projectable.
- **The subagent delegation flow** (parent routing work to named subagents across
  phases) — describes machinery that does not exist here.
- **Five skills depending on Obsidian tooling** — `obsidian-bases`,
  `obsidian-cli`, `obsidian-markdown`, `json-canvas`, `defuddle` — excluded by
  decision.
